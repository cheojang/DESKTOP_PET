# TDD 교리 (Red → Green → Refactor + Tidy First)

Kent Beck TDD + Tidy First 기반. 코드 에이전트(빌더·리뷰어)가 준수한다.

## TDD 사이클
1. **Red** — 가장 단순한 실패 테스트 먼저. 동작 설명 이름(`test_lands_on_floor_enters_idle`). 실패 명확히.
2. **Green** — 통과시킬 **최소** 코드만.
3. **Refactor** — 통과 상태에서만. 한 번에 하나씩, 매 단계 후 테스트 재실행. 중복 제거·명료성 우선.

매번 한 테스트 → 통과 → 구조 개선. 항상 전체 테스트 실행.

## Tidy First — 구조/행위 분리
- **구조 변경**: 동작 불변 — 리네임·추출·이동.
- **행위 변경**: 기능 추가/수정.
- 한 커밋에 혼합 금지. 둘 다 필요하면 구조 먼저. 구조 변경은 전후 테스트로 동작 불변 검증.

## 커밋 규율
커밋 조건(전부 충족): ① 모든 테스트 통과 ② 린터/구문 경고 0 ③ 단일 논리 단위 ④ 메시지에 구조/행위 명시. 작고 잦은 커밋. **에이전트는 커밋·브랜치 금지** — 오케스트레이터가 검수·승인 후 단일 커밋.

## 코드 품질
중복 박멸 · 이름과 구조로 의도 표현 · 의존성 명시 · 작고 단일책임 메서드 · 상태/부수효과 최소 · 가장 단순한 해법.

## TDD 적용 한계 (과적용 금지)
테스트 가능한 동작이 있는 **코드**에만 적용.
- **적용 대상(이 프로젝트):** `pet_state_machine.py`(물리·전이·CPU매핑), `win_api`/`get_window_floors` 좌표·자기창 제외 로직, `character.py` 팩 로딩, `face_warp` 크롭 기하 등 순수 로직.
- **비적용:** GUI 창·렌더 시각·트레이 — 설계서·UI 감각엔 TDD 강제 X. 그땐 `dev-rules.md`의 목표 주도(성공 기준 정의)로 대체하고 **오프스크린 스모크 + 수동 실행**으로 검증.
